# 普通用户与用户编号

Dawn内置`users`普通用户体系。业务模型可以嵌入`models.User`并添加字段，后台管理员使用`models.AdminUser`和`admin_users`，两个体系的登录凭证与权限分别管理。`AdminUser.UserID`可以关联普通用户，但关联本身不授予后台权限。

## 用户类型

`type`包含`guest`访客、`member`普通用户和`ai`智能体。客服应用各自拥有一个AI用户，访客资料按应用保存在`user_traits`。后台权限检查使用管理员身份，不依赖普通用户类型。

## 登录与访客恢复

普通用户和访客登录状态使用PrismGo Session＋Redis，SQL只保存用户、资料和聊天业务记录。账号登录与客服应用凭证分别校验，不能跨应用借用凭证；外部身份仍须经过签名或本站一次性票据校验。

浏览器保存访客随机凭证，默认有效期180天。同一浏览器在凭证有效时重新打开聊天，会恢复原身份与聊天记录；清除浏览器存储或丢失Redis登录数据后，匿名身份不能仅凭昵称、IP、UA重新认领。已验证账号重新认证后可继续访问原记录。本站游客注册时原地升级，编号与历史保持不变；登录已有账号时归并当前应用内的游客咨询，事务提交后撤销旧凭证。双向接入见[网站与客服身份](support-identity.md)。

登录、注销接口及框架配置见[客服与实时聊天](chat.md)和[登录与会话](authorization.md#登录与会话)。

## 访客管理

后台访客管理是全局用户目录，通过`dawn.members.list/create/update/delete`分别控制查看、新增、修改和删除权限。`GET /admin/members`支持`query`、`type`、`status`筛选和标准分页，默认每页10条、ID倒序；`GET /admin/members/{id}`读取详情。

`POST /admin/members`创建普通用户，必填`username`和`password`，用户名3～80个字符、密码至少6个字符且不超过72字节。资料字段为`nickname`、`avatar`、`email`、`mobile`、`locale`、`status`，分别限制为100、500、180、40、16个字符和启用1/停用2。用户类型、内部ID、对外编号与审计时间由服务端维护。

`PATCH /admin/members/{id}`只修改提交的资料字段，`PUT`重置全部资料字段，省略值恢复默认。`DELETE /admin/members/{id}`删除单条，`DELETE /admin/members?ids=1,2`事务删除指定多条，任一记录不存在则整批不删除。停用和删除同时撤销该用户的登录凭证。

## 对外编号

`users.id`是内部主键，`users.unique_id`是由主键转换而来的唯一字符串。使用ORM逐个创建`models.User`时，创建钩子在同一事务中写入编号；直接SQL写入时，由业务方在事务内调用相同转换方法写入。

首次安装生成一次随机256位密钥，保存在`admin_settings`的`__user_identity`记录中，不出现在系统配置表单，也不提供编辑接口。再次安装不覆盖已有配置。编号采用AES-FF1九进制保留格式加密，字符集为`012356789`，无前导0。从7位开始，每个连续原始ID区间固定对应一种编号长度，用满后逐位增加；规则固定在框架代码中，不提供长度配置。

`identity.Load(ctx, db)`复用全局配置的`ForeverSettings`分组Hash，配置组为`__user_identity`，字段为`key`，不另建编号缓存。缓存使用应用已有Redis连接，按应用名与环境隔离，无过期时间，保留`__revision`版本。双下划线开头的内部配置组不在后台展示、编辑或清理。缓存命中不查询SQL；缓存丢失后读取同一数据库记录并恢复缓存，不生成新密钥。`db:seed`提交后清理该组缓存，避免重新安装时沿用旧配置。

| 整数绝对值 | 编号位数 |
| --- | --- |
| 1～1,889,568 | 7 |
| 1,889,569～18,895,680 | 8 |
| 18,895,681～171,950,688 | 9 |
| 171,950,689～1,549,445,760 | 10 |
| 1,549,445,761～13,946,901,408 | 11 |

每档每种符号新增容量为`32 × 9^(位数-2)`，区间连续、互不重叠，不跳过任何原始ID。相邻档位新增容量为前一档的9倍；7～10位累计覆盖约15.49亿个正数ID，负数另有相同容量。最大21位，覆盖除0以外的完整`int64`范围。

位数只由原始ID的绝对值所属区间决定，不随机选择，也不依赖当前用户数或最大ID。固定密钥下，同一整数始终对应同一编号，不同整数不会生成相同编号；正负同绝对值的编号长度相同。

中间位取索引`len(value)/2`，从0开始；奇数表示正数，偶数表示负数，偶数长度使用中间偏右的位置。用户主键仍为正数，负数供开发者在其他业务中使用。

转换先减去区间起点，得到从0开始的序号，再映射到合法字符域并重复FF1置换直到满足首位和符号位约束。还原时按编号长度找到区间，逆置换恢复序号，再加回区间起点并恢复符号。整个非零`int64`输入范围都可正向转换并还原；字符规则以外及未分配的编号字符串可能无效。解码不访问数据库查询原始ID。

**该记录必须随数据库一起备份，不得修改或删除。** 缓存未命中且安装记录缺失，或配置校验不通过时返回错误，不会自动生成另一套密钥。`dawn:install`只适用于完整初始化；已有用户的数据库恢复必须恢复对应配置，并清除旧环境中的编号缓存。重新建库使用`migrate:fresh --seed`，使结构和缓存一起更新。

```go
import "github.com/dawnim/dawn-server/support/identity"

codec, err := identity.Load(ctx, db)
if err != nil {
    return err
}
uniqueID, err := codec.ID2Big(int64(user.ID))
if err != nil {
    return err
}
internalID, err := codec.Big2ID(uniqueID)
if err != nil {
    return err
}
_ = internalID

// 通用转换也支持负数，解码结果仍为int64。
encoded, err := codec.ID2Big(-123)
if err != nil {
    return err
}
original, err := codec.Big2ID(encoded) // original == -123
if err != nil {
    return err
}
_ = original
```

同一批转换只调用一次`Load`并复用`codec`。`ID2Big`和`Big2ID`只做内存计算，不访问数据库或Redis；已取得的`codec`支持并发使用。独立程序也可以直接使用`identity.Codec{Key: key}`，`key`为原安装密钥的64位十六进制字符串，无需初始化数据库或缓存。

公开账号资料与客服会话不返回内部用户主键，访客实时身份和消息主体使用`unique_id`；后台管理仍可以按内部主键操作。

编号在JSON和前端中始终使用字符串，避免超过JavaScript安全整数范围时丢失精度。`ID2Big`接受非零`int64`，`Big2ID`返回`int64`，包括最小负数。0、非法字符、前导0和超出档位容量的输入返回可按请求语言翻译的错误。

编号置换隐藏档位内主键的连续变化，长度会透露绝对值的大致区间，中间位会透露正负。编号不是登录凭证，也不提供防篡改校验，查询和写入仍须检查登录凭证及数据范围。已存编号的密钥和规则必须保持不变；更换规则需统一重建编号及引用，不保留旧编码兼容。

## 框架表标识

内置表沿用`admin_*`、`chat_*`、`users`等职责名称，不额外添加产品前缀。支持表注释的数据库统一使用`系统:`开头，例如`系统:普通用户表`；业务方自建表使用自己的业务注释。SQLite不支持原生表注释。
